# План реализации

Поэтапный план: каждый этап даёт работающий результат, который можно проверить,
прежде чем двигаться дальше.

## Этап 0 — каркас Django

- Проект Django, `pyproject.toml`, зависимости из
  [ARCHITECTURE.md](ARCHITECTURE.md).
- `config/settings.py` с `django-environ`, пример `.env`.
- Приложение `newsroom`, подключение БД (SQLite в dev), `manage.py`.
- `pytest` + `pytest-django`, базовый CI.

**Проверка:** проект поднимается, `python manage.py migrate` проходит, тесты
запускаются.

## Этап 1 — админ-панель и модели настроек

- Модели `TargetSite`, `WordPressCategory`, `Source` (см.
  [DATA_MODEL.md](DATA_MODEL.md)), первая миграция.
- Регистрация в `admin.py`; шифрование пароля WP
  (`django-encrypted-model-fields`).
- `createsuperuser`; вход в `/admin`.
- У `Source` поле `target_category` — выпадающий список, отфильтрованный по
  выбранному сайту.

**Проверка:** администратор входит в админку, добавляет сайт и RSS-ленту,
указывает целевую рубрику.

## Этап 2 — сбор и дедупликация

- `sources/base.py` + `sources/rss.py` (feedparser).
- `dedup.py` (нормализация URL + хеш).
- Сохранение статей в статусе `fetched`, пропуск дубликатов.

**Проверка:** запуск по добавленной в админке ленте наполняет `Article`,
повторный запуск не создаёт дублей.

## Этап 3 — извлечение текста

- `extract/article.py` (trafilatura) с обработкой ошибок.
- Переход `fetched → extracted` / `failed`.

**Проверка:** у собранных статей появляется `full_text`; непарсимые помечаются
`failed` с причиной.

## Этап 4 — абстракция рерайта

- `rewrite/base.py` (ABC + DTO), `rewrite/factory.py`.
- `rewrite/anthropic.py` (структурированный JSON-ответ), затем
  `rewrite/openai.py`.
- Промпт с сохранением фактов, HTML-телом, SEO-мета и атрибуцией.
- Переход `extracted → rewritten`, запись `RewrittenContent` с учётом токенов.

**Проверка:** для статьи генерируется корректный `RewriteResult`; смена
провайдера в настройках не требует правок в конвейере.

## Этап 5 — публикация в WordPress

- `publish/base.py` + `publish/wordpress.py` (REST API, Application Passwords).
- Действие в админке «Синхронизировать рубрики» (заполняет `WordPressCategory`).
- Публикация в рубрику из `Source.target_category`; переход `rewritten →
  published`, запись в `Publication`.
- По умолчанию публикация в `draft`.

**Проверка:** пост появляется в WordPress как черновик в нужной рубрике, с
заголовком, телом, тегами и ссылкой на первоисточник.

## Этап 6 — оркестрация и расписание

- `pipeline.py` (полный конвейер end-to-end по одному источнику).
- `scheduler.py` + `django-apscheduler`; команды `run_pipeline`,
  `run_scheduler`.
- Действия в админке: «Собрать сейчас» (источник), «Повторить» (упавшая статья),
  «Проверить подключение» (сайт).

**Проверка:** планировщик по расписанию проходит весь путь от RSS до черновика;
ручные действия из админки работают.

## Этап 7 — эксплуатация (по мере необходимости)

- Метрики (обработано, ошибки, затраты токенов) в админке.
- Несколько источников и несколько сайтов.
- Переключение автопубликации (`draft → publish`) после оценки качества.
- При росте нагрузки — Celery + beat вместо in-process планировщика,
  PostgreSQL, контейнеризация (Docker), gunicorn/ASGI.
- Опционально: подбор/генерация изображения записи, ручная модерация перед
  публикацией, дедупликация по содержимому (не только по URL).

## Принципы

- **Вертикальные срезы:** на каждом этапе — работающий, проверяемый кусок.
- **Абстракции на границах:** источники, рерайтеры и публикаторы — за
  интерфейсами, чтобы добавлять новые без переписывания ядра.
- **Безопасный дефолт:** черновики и `draft`-публикация, пока не подтверждено
  качество рерайта.
- **Настройки — в админке, секреты — в окружении.**
